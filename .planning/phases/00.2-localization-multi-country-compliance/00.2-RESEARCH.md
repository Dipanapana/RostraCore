# Phase 0.2: Localization & Multi-Country Compliance - Research

**Researched:** 2026-02-04
**Domain:** Internationalization (i18n), multi-currency payroll, labor law compliance engines, exchange rates
**Confidence:** HIGH (core stack) / MEDIUM (architecture patterns) / MEDIUM (pitfalls)

## Summary

This phase layers multi-country support onto an existing Next.js 14 + FastAPI + PostgreSQL workforce management platform that is currently hardcoded for South Africa (ZAR currency, BCEA labor laws, SA PAYE/UIF/SDL tax). The existing codebase has SA-specific logic deeply embedded: `sa_payroll_service.py` with hardcoded tax brackets, `bcea_compliance_service.py` with SA labor rules, and frontend `formatCurrency` functions that prefix `R ` to all amounts.

The standard approach is: (1) **next-intl** for frontend i18n with the "without routing" pattern (user-preference locale, no URL prefixes), (2) **Intl.NumberFormat** for currency-specific formatting (locked decision), (3) **Python Decimal** with explicit rounding for all monetary backend calculations, (4) **Babel (Python)** for backend locale formatting, (5) a **JSON-driven country configuration** system for tax rules and labor laws, (6) **Open Exchange Rates** or **Frankfurter** for exchange rate data, and (7) a **rules engine pattern** to replace hardcoded SA compliance with configurable country-specific rule sets.

**Primary recommendation:** Build a config-driven country engine where adding a new country means uploading a JSON file -- not writing code. Extract the existing SA payroll and BCEA services into the first "country plugin" and make the engine generic.

### Pattern 2: Tax Engine with Strategy Pattern

**What:** A generic `TaxEngine` class that loads country config and computes taxes using the same algorithm shapes (bracket-based, flat-rate, social contributions) parameterized by config data.

**When to use:** Replacing the hardcoded `SAPayrollService`.

**Example:**

```python
# backend/app/services/tax_engine.py
from decimal import Decimal, ROUND_HALF_UP
from typing import Dict

class TaxEngine:
    """Generic tax calculation engine driven by country config."""

    def __init__(self, country_config: dict):
        self.config = country_config
        self.tax_rules = country_config["tax_rules"]

    def calculate_income_tax(
        self,
        gross_monthly: Decimal,
        age: int = 35
    ) -> Dict[str, Decimal]:
        """Calculate income tax using bracket config."""
        tax_config = self.tax_rules["income_tax"]

        if tax_config["type"] == "bracket":
            return self._calculate_bracket_tax(gross_monthly, age, tax_config)
        elif tax_config["type"] == "flat":
            return self._calculate_flat_tax(gross_monthly, tax_config)
        else:
            raise ValueError(f"Unknown tax type: {tax_config['type']}")

    def _calculate_bracket_tax(
        self,
        gross_annual: Decimal,
        age: int,
        config: dict
    ) -> Dict[str, Decimal]:
        """Bracket-based progressive tax (SA PAYE, US Federal, UK PAYE, etc.)."""
        # ... generic bracket calculation using config["brackets"]
        pass

    def calculate_social_contributions(
        self,
        gross_monthly: Decimal
    ) -> list[Dict[str, Decimal]]:
        """Calculate all social contributions from config."""
        results = []
        for contrib in self.tax_rules.get("social_contributions", []):
            employee_amount = Decimal("0")
            employer_amount = Decimal("0")

            earnings = min(
                gross_monthly,
                Decimal(str(contrib.get("max_earnings", float("inf"))))
            )

            if contrib.get("employee_rate"):
                employee_amount = (
                    earnings * Decimal(str(contrib["employee_rate"]))
                ).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)

            if contrib.get("employer_rate"):
                employer_amount = (
                    earnings * Decimal(str(contrib["employer_rate"]))
                ).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)

            results.append({
                "name": contrib["name"],
                "employee_amount": employee_amount,
                "employer_amount": employer_amount,
                "description": contrib.get("description", "")
            })
        return results
```

### Pattern 3: Currency Formatting with Origin-Country Locale (Locked Decision)

**What:** Currency is always formatted using the locale of the currency's origin country, not the user's UI locale.

**When to use:** All currency display throughout the application.

**Example:**

```typescript
// frontend/src/lib/currency.ts

// Map of currency code -> locale for formatting
const CURRENCY_LOCALE_MAP: Record<string, string> = {
  ZAR: 'en-ZA',   // South African Rand
  USD: 'en-US',   // US Dollar
  GBP: 'en-GB',   // British Pound
  EUR: 'de-DE',   // Euro (German convention as default)
  NGN: 'en-NG',   // Nigerian Naira
  KES: 'en-KE',   // Kenyan Shilling
};

export function formatCurrency(
  amount: number,
  currencyCode: string
): string {
  const locale = CURRENCY_LOCALE_MAP[currencyCode] || 'en-US';

  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency: currencyCode,
  }).format(amount);
}

// Examples:
// formatCurrency(1234.56, 'ZAR') -> "R 1 234,56"
// formatCurrency(1234.56, 'USD') -> "$1,234.56"
// formatCurrency(1234.56, 'EUR') -> "1.234,56 EUR"  (de-DE locale)
```

### Pattern 4: next-intl Without i18n Routing (User-Preference Locale)

**What:** Use next-intl's "without routing" mode where locale comes from user preferences (stored in DB / cookie), not from URL paths. No `[locale]` route segment needed.

**When to use:** This application is behind auth, users set their language preference. No SEO benefit from locale URLs.

**Why:** The existing app has no `[locale]` route segment. Adding one would require restructuring all routes. The "without routing" pattern avoids this entirely and is the officially supported approach for apps where locale is based on user settings rather than URL.

**Example:**


### Pattern 5: Exchange Rate Caching with Staleness Fallback

**What:** Fetch exchange rates from API, cache in database with timestamp. Use cached rate if API is down. Lock rate at payroll generation time.

**When to use:** All currency conversions.

**Example:**

```python
# backend/app/services/exchange_rate_service.py
class ExchangeRateService:
    CACHE_DURATION_HOURS = 4  # Refresh every 4 hours
    PRIMARY_API = "https://open.er-api.com/v6/latest/{base}"
    FALLBACK_API = "https://api.frankfurter.dev/v1/latest?base={base}"

    async def get_rate(
        self, from_currency: str, to_currency: str, db: Session
    ) -> Decimal:
        """Get exchange rate with caching and fallback."""
        cached = self._get_cached_rate(from_currency, to_currency, db)
        if cached and not self._is_stale(cached):
            return cached.rate

        # Try primary API
        try:
            rate = await self._fetch_from_api(
                self.PRIMARY_API, from_currency, to_currency
            )
        except Exception:
            # Try fallback
            try:
                rate = await self._fetch_from_api(
                    self.FALLBACK_API, from_currency, to_currency
                )
            except Exception:
                if cached:
                    return cached.rate  # Stale but available
                raise ExchangeRateUnavailable(
                    f"No rate available for {from_currency}->{to_currency}"
                )

        # Cache the new rate
        self._cache_rate(from_currency, to_currency, rate, db)
        return rate
```

### Anti-Patterns to Avoid

- **Hardcoding country logic in service files:** The current `sa_payroll_service.py` pattern is exactly what to avoid going forward. Extract to config, don't create `us_payroll_service.py`, `uk_payroll_service.py`, etc.
- **Using float for money:** The existing `PayrollSummary` model uses `Float` columns for `gross_pay` and `net_pay`. These MUST be migrated to `Numeric(12, 2)` or integer-cents storage.
- **Formatting currency with string concatenation:** The current `R ${amount.toFixed(2)}` pattern is fragile. Always use `Intl.NumberFormat`.
- **Storing amounts without currency code:** Every monetary column needs an associated currency code column (or the org's default currency must be deterministic).
- **Converting currencies multiple times:** Convert once, store both original and converted amounts with the rate used.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Currency number formatting | Regex-based formatting like current `formatCurrency` | `Intl.NumberFormat` with locale + currency params | Handles 170+ currencies, decimal separators, symbol placement, minor unit digits automatically |
| Translation string management | Custom key-value lookup | next-intl with JSON message files | Handles pluralization, interpolation, nested namespaces, SSR/CSR consistency |
| Locale data (country names, currency names) | Hardcoded lookup tables | `Intl.DisplayNames` (browser) + Babel CLDR data (Python) | CLDR is the canonical source with 700+ locales |
| Exchange rate fetching | Raw HTTP calls with no caching | Dedicated service with cache table + staleness fallback | Rate limiting, API failures, stale data scenarios are common |
| Tax bracket calculation | Separate service per country | Generic bracket engine with JSON config | Same algorithm shape (progressive brackets) applies to 100+ countries |
| Public holiday detection | Hardcoded date lists | JSON config per country per year + holiday calculation rules | Some holidays are date-based, some are Easter-relative, some are observation-adjusted |
| Float-to-Decimal conversion | `Decimal(float_value)` | `Decimal(str(float_value))` or store as integer cents | `Decimal(0.1)` != `Decimal("0.1")` -- float precision leaks into Decimal |

**Key insight:** Localization and currency formatting are among the most standardized problem domains in software. The CLDR (Unicode Common Locale Data Repository) contains formatting rules for every locale. Intl.NumberFormat and Babel both consume CLDR data. Hand-rolling any of this guarantees bugs with edge-case locales.

## Common Pitfalls

### Pitfall 1: Float Columns for Money

**What goes wrong:** The existing `PayrollSummary` model uses `Float` for `gross_pay`, `net_pay`, `overtime_hours`. Float arithmetic accumulates rounding errors. A payroll run across 200 employees can drift by multiple cents/rands.
**Why it happens:** Float is the "easy" column type. Decimal/Numeric requires explicit precision.
**How to avoid:** Migrate ALL monetary columns to `Numeric(12, 2)` (or `Numeric(14, 4)` for intermediate calculations). Use `Decimal` in Python, never `float` for money.
**Warning signs:** Payroll totals that don't add up, off-by-one-cent errors in bulk operations.

### Pitfall 2: Rounding at the Wrong Stage

**What goes wrong:** Rounding intermediate calculations (e.g., rounding hourly rate * hours, then rounding again after tax) causes cascading errors.
**Why it happens:** Developers round early for "clean" numbers.
**How to avoid:** Use `Decimal` with 4+ decimal places for ALL intermediate calculations. Only round to 2 decimal places at the final display/storage step. Use `ROUND_HALF_UP` consistently (not banker's rounding) for payroll -- this is the most common regulatory requirement.
**Warning signs:** Different totals depending on calculation order.

### Pitfall 3: Assuming All Currencies Have 2 Decimal Places

**What goes wrong:** Japanese Yen (JPY), Korean Won (KRW), and several others have 0 decimal places. Kuwaiti Dinar (KWD) has 3. Formatting JPY as "165.00" is incorrect.
**Why it happens:** Most common currencies (USD, EUR, GBP, ZAR) use 2 decimals.
**How to avoid:** Store the minor unit count in the currency config. `Intl.NumberFormat` handles this automatically when given the currency code. On the backend, Babel's `format_currency` also handles this.
**Warning signs:** "JPY 100.00" displayed anywhere.

### Pitfall 4: Forgetting to Store the Exchange Rate Used

**What goes wrong:** A payroll run converts ZAR to USD at a certain rate. Later, the rate changes. Without storing which rate was used, you can't recreate/audit the payroll.
**Why it happens:** Developers only store the converted amount, not the conversion metadata.
**How to avoid:** Every conversion must store: original_amount, original_currency, converted_amount, converted_currency, exchange_rate_used, conversion_timestamp.
**Warning signs:** Audit questions about "why does this number not match the current rate?"

### Pitfall 5: i18n Routing Restructure

**What goes wrong:** Adding `[locale]` route segment to an existing Next.js app breaks all existing routes, requires moving every page file, and complicates the Tauri desktop build.
**Why it happens:** Many i18n tutorials assume a greenfield project.
**How to avoid:** Use next-intl's "without i18n routing" mode. Store locale in user preferences/cookie. No URL changes needed.
**Warning signs:** Existing bookmarks/links breaking, desktop app routing issues.

### Pitfall 6: Translating Dynamic Content Without a Strategy

**What goes wrong:** Translating static UI labels is straightforward, but role names, shift types, department names, and other org-defined content can't be pre-translated.
**Why it happens:** Mixing static i18n with dynamic content translation.
**How to avoid:** Separate static UI translations (JSON files, next-intl) from dynamic content. Dynamic content uses a `display_name_i18n` JSON column pattern: `{"en": "Day Shift", "af": "Dagskof", "zu": "Ishifu yasemini"}`. Fall back to the org's default language.
**Warning signs:** Half-translated pages, untranslatable user-created content.

### Pitfall 7: Tax Year Misalignment

**What goes wrong:** South Africa's tax year runs March-February. The US runs January-December. UK runs April-March. Assuming calendar year breaks tax calculations.
**Why it happens:** Developers default to calendar year boundaries.
**How to avoid:** Store `tax_year_start` and `tax_year_end` in country config. All tax calculations reference the country's fiscal calendar.
**Warning signs:** Incorrect bracket application near year boundaries.

```typescript
import { getRequestConfig } from 'next-intl/server';

const SUPPORTED_LOCALES = ['en', 'af', 'zu', 'fr', 'pt', 'sw'] as const;

export default getRequestConfig(async () => {

});
```

### Backend Currency Formatting with Babel

```python
# Source: https://babel.pocoo.org/en/latest/api/numbers.html
from babel.numbers import format_currency

# Format follows currency's origin country (locked decision)
CURRENCY_LOCALE_MAP = {
    "ZAR": "en_ZA",
    "USD": "en_US",
    "GBP": "en_GB",
    "EUR": "de_DE",
    "NGN": "en_NG",
    "KES": "en_KE",
}

def format_money(amount: Decimal, currency_code: str) -> str:
    """Format a monetary amount using the currency's origin locale."""
    locale = CURRENCY_LOCALE_MAP.get(currency_code, "en_US")
    return format_currency(float(amount), currency_code, locale=locale)
```

```python
    multi_currency_enabled = Column(Boolean, default=False, nullable=False)
```

## Discretionary Recommendations

Based on research, here are recommendations for the areas left to Claude's discretion:

### Exchange Rate Strategy: Cached with Refresh + Locked at Payroll

**Recommendation:** Use cached exchange rates refreshed every 4 hours. When generating payroll, lock the rate at the moment of payroll generation and store it with the payroll record. This balances accuracy (rates updated multiple times daily) with offline support (cached rates available) and auditability (locked rate stored with payroll).

### Exchange Rate API Provider: Open Exchange Rates (primary) + Frankfurter (fallback)

**Recommendation:**
- **Primary:** ExchangeRate-API open endpoint (`open.er-api.com`) -- free, no API key, 150+ currencies, soft rate limits. Good for starting.
- **Fallback:** Frankfurter (`api.frankfurter.dev`) -- free, no API key, ECB-sourced, fewer currencies but very reliable.
- **Production upgrade path:** Open Exchange Rates paid plan ($12/mo) when needing 10-minute updates or more currencies.

### Multi-Currency Per Org: Yes, with Primary Currency

**Recommendation:** An organization has a `primary_currency` (the currency of their country) and can optionally enable `multi_currency_enabled`. When enabled, individual employees can be assigned a `pay_currency` that differs from the org's primary. Payroll reports show amounts in both currencies. This is common in companies with expats or cross-border operations.

### Rounding Rules: ROUND_HALF_UP Consistently

**Recommendation:** Use `ROUND_HALF_UP` (traditional rounding) for all payroll calculations. This is the most widely expected behavior in financial/payroll contexts. Store intermediate calculations with 4 decimal places, round to the currency's minor unit (usually 2) only at the final step.

### Tax Calculation Approach: Table-Based (JSON Config)

**Recommendation:** Use table-based (JSON bracket definitions) rather than formula-based. Almost all countries use progressive bracket systems that can be represented as tables. The JSON structure shown in the Architecture Patterns section handles this. Formula-based would only be needed for very unusual tax regimes.

### Labor Law Validation Timing: On Roster Confirm (primary) + Warning on Save

**Recommendation:** Validate labor law compliance at two points:
1. **On shift save (soft warning):** Show amber warnings for potential violations but allow saving.
2. **On roster confirm (hard validation):** Block confirmation if there are hard violations. This prevents accidental compliance failures while allowing flexibility during planning.

### Labor Law Violation Handling: Configurable Per Rule

**Recommendation:** Each labor law rule in the country config should have a severity level: `"block"`, `"warn"`, or `"info"`. The org admin can override severity (downgrade block to warn, but not remove entirely). This matches the existing `RosterPreferences` pattern where constraints have levels (`hard`/`soft`/`warning`/`disabled`).

### Language Switching UX: Immediate Apply

**Recommendation:** Language changes should apply immediately (no page reload needed with next-intl). The user's preference is saved to their profile (backend) and a cookie (for SSR). Only static UI text is translated via i18n files. Dynamic content (org-specific names) falls back to the org's default language.

### i18n Library: next-intl (confirmed by research)

**Recommendation:** next-intl is the clear winner for Next.js 14 App Router. It is the only mature library with native Server Component support. Use the "without routing" setup to avoid restructuring existing routes.

### Translation Coverage: UI Only (Phase 1), Dynamic Content Later

**Recommendation:** Start with static UI text translation only (labels, buttons, messages, error strings). Dynamic content translation (role names, shift types) should use a `display_name_i18n` JSON column pattern but can be deferred to a follow-up iteration. The i18n infrastructure will support both.

### Country Configuration Format: JSON with Versioned Schema

**Recommendation:** Use the JSON structure shown in Architecture Patterns. Store in both filesystem (for version control / defaults) and database (for runtime / admin modifications). Add a `config_version` field for migration compatibility. Validate with a JSON Schema or Pydantic model before accepting uploads.

## Open Questions

1. **Existing Float columns migration strategy**
   - What we know: `PayrollSummary` uses Float for money. Other models may too.
   - What's unclear: Full inventory of Float-for-money columns across all models.
   - Recommendation: Audit all models in Step 1 of implementation. Create a single Alembic migration to convert all monetary Float columns to Numeric.

2. **Historical payroll data after currency migration**
   - What we know: Existing payroll data is in ZAR with no currency column.
   - What's unclear: Whether historical data needs retroactive currency tagging.
   - Recommendation: Add `currency_code` column with default 'ZAR' to existing payroll tables. Historical data is implicitly ZAR.

3. **Desktop (Tauri) app implications**
   - What we know: The app has a Tauri desktop build with static export mode.
   - What's unclear: Whether next-intl's cookie-based locale detection works in Tauri's webview.
   - Recommendation: Test during implementation. May need to fall back to localStorage + client-side locale detection for desktop builds.

4. **Translation workflow tooling**
   - What we know: next-intl uses JSON message files. Babel uses PO/MO files.
   - What's unclear: Whether a translation management platform (Crowdin, Lokalise) is needed now.
   - Recommendation: Start with manual JSON files. Defer translation platform to when 3+ languages are actively maintained.

5. **VAT/GST handling**
   - What we know: Current system has a single `VAT_PERCENTAGE` system setting (15% for SA).
   - What's unclear: Whether invoice-level VAT/GST needs to be country-configurable in this phase.
   - Recommendation: Include VAT rate in country config but defer full invoice localization to billing phase.
