# Phase 0.2: Localization & Multi-Country Compliance - Context

**Gathered:** 2026-02-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Support ANY country's currency, tax system, labor laws, and language. Enable organizations to operate in multiple countries with localized compliance. NOT a multi-tenant rewrite - layering localization onto existing org structure.

**What this phase delivers:**
- Multi-currency support with exchange rate handling
- Multi-tax engine supporting different countries' payroll tax rules
- Labor law rules engine (overtime, max hours, rest periods by country)
- UI internationalization (i18n) for multiple languages

**Explicitly OUT of scope:**
- Multi-country payroll consolidation/reporting (future phase)
- Country-specific industry templates (future enhancement)
- Multi-timezone scheduling (defer to later if needed)

</domain>

<decisions>
## Implementation Decisions

### Currency Display Format
- **Format follows currency's origin country**, not user's locale
  - USD displays as "$1,234.56" (US format)
  - ZAR displays as "R1 234,56" (SA format with spaces)
  - EUR displays as "€1.234,56" (European format)
- Use Intl.NumberFormat with currency-specific locale for formatting

### Claude's Discretion
The following areas are left to Claude's judgment based on research and best practices:

- **Exchange rate strategy** - Live API vs cached with refresh (balance accuracy, offline support, cost)
- **Payroll conversion timing** - Convert at run time vs lock rate earlier (accuracy vs predictability)
- **Multi-currency per org** - Whether one org can pay employees in different currencies (research common patterns)
- **Exchange rate API provider** - Which service to use (Open Exchange Rates, CurrencyLayer, Fixer.io, or other)
- **Rate caching duration** - How often to refresh if using cached rates
- **Rounding rules** - How to handle fractional cents/pence in calculations
- **Tax calculation complexity** - Formula-based vs table-based approach for different countries
- **Labor law validation timing** - When to validate rules (on save, on roster confirm, on payroll)
- **Labor law violation handling** - Warning vs blocking when rules violated
- **Language switching UX** - Immediate apply vs next login, what gets translated
- **i18n library choice** - next-i18next, next-intl, lingui, or other
- **Translation coverage** - UI only vs dynamic content (role names, shift types, etc.)
- **Country configuration format** - JSON structure for tax rules, labor laws, etc.

</decisions>

<specifics>
## Specific Ideas

- Currency formatting should respect each currency's conventions (R1 234,56 for ZAR is correct, not R1,234.56)
- South Africa remains primary market, but system must work equally well for US, UK, Nigeria, Kenya, etc.
- Adding a new country should be config-driven (JSON file upload), not require code changes

</specifics>
